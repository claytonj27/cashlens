# ADR 0009: Text-PDF statement imports, duplicate policy and lease-guarded staging

- Status: accepted
- Date: 2026-09-13
- Deciders: project author
- Related: [ADR 0008](0008-statement-imports-and-source-adapters.md), [data contract](../data-contract.md), [statement import plan](../planning/CashLens-Statement-Import-Plan.md)

## Context

Milestone 7 adds a second deterministic statement parser for text-based PDF
statements on top of the M6 import pipeline, and corrects two things the M6
review left open: the cross-format duplicate policy (a PDF and a CSV of the
same statement must not double-count, but similarity alone must never merge
rows) and lease protection for the mutations of a processing step.

## Decisions

Dependency
- `pypdf` (pure Python, BSD), pinned in `requirements.txt`. Measured on the
  development machine (macOS, Python 3.12): wheel 394 KB, import 122 ms,
  parse plus normalize 27 ms for the pack's four-page file and 4 to 8 ms for
  single-page files and fixtures. Observed on the branch preview through the
  web proxy for the four-page pack file: upload to Storage 0.3 s, extract and
  stage 1.5 to 1.7 s, confirm 1.3 s (single samples, including the proxy and
  the function; not a benchmark). No OCR library, no model calls.

Supported and refused inputs
- Supported: text-based statements for one USD checking or savings account
  whose text layer yields one transaction per line with a table header naming
  a date column and an amount, debit or credit column; optional running
  balance and reference columns; continuation lines for wrapped descriptions;
  a header block or footer stating the period, opening balance, closing
  balance, totals and transaction count. Repeated page banners, repeated
  table headers and repeated summary blocks add nothing. Support is claimed
  only for the layouts covered by committed fixtures (`fixtures/statements/`,
  generated by `app/synthetic/statements.py`): the pack's layout with wrapped
  descriptions and identical repeated payments across two pages, a
  debit/credit layout with US dates and a footer balance, and a layout with
  no balances. Nothing here has been validated against a real bank's export.
- Refused with an explained code, never guessed: not a PDF at all
  (`not_pdf`), damaged or truncated files (`pdf_malformed`), password
  protection that an empty password does not open (`pdf_encrypted`; the owner
  removes the password in a viewer, passwords are never accepted), no usable
  text layer such as scans and photos (`pdf_no_text_layer`; OCR is not
  offered), more than 20 pages (`too_many_pages`), more than 500 KB of text
  (`extraction_text_too_large`), credit-card statements and invoices
  (`unsupported_document_type`, keyword heuristics), and text without a
  transaction table (`pdf_layout_unsupported`, with the first lines read so
  the owner sees why). The format is decided from the bytes, never from the
  file name or the declared MIME type.

Extraction (`app/imports/pdfparse.py`, version `pdf-1`)
- Text chunks with positions from pypdf's visitor; lines by vertical
  position; the table header's x positions define column ranges; chunks are
  assigned to columns by position; lines without a date or amount join the
  description above; summary lines are metadata, not rows. The output is the
  CSV parser's `Table`, so mapping, normalization, flags, matching, staging,
  review and confirmation are shared code.
- Statement metadata is read independently of the rows: period, opening and
  closing balances, total credits and debits, transaction count and account
  digits. Reconciliation compares the rows with those printed figures
  (`statement_totals`); a CSV without them falls back to its running balance
  column; with neither, reconciliation is reported as unavailable, never
  assumed. Mismatches name the problem (rows do not bridge the balances,
  totals differ, count differs, running balance breaks) and nothing is
  invented to make the figures balance. Unparsed transaction-like lines stay
  as blocking rows; nothing is discarded silently.
- Balances read from a statement are stored as `statement_opening` and
  `statement_closing` observations with bank-observed provenance and the
  printed period, and shown as historical figures.

Provenance
- Every staged row keeps its page number and locator (`page N line M`) and
  the text of its cells as read; confirmed rows keep them after the object is
  deleted, and the evidence panel shows the file, format, row, page and line.
  The application never promises to show the original PDF later.

Duplicate policy (`app/imports/matching.py`)
- Identity evidence: the same account and the same trusted source reference
  on both the new row and an existing transaction. Identical values are
  `already_imported` and default to linking (extra provenance, no new
  transaction, no decision needed). Different values are
  `conflicting_revision` and need an owner decision: keep as new, link, or
  replace the existing values.
- Shape evidence only (date, amount, normalized description) is never proof:
  such rows are `duplicate_candidate` rows that need an owner decision.
  Pairing is one to one in file order, so k identical-looking rows against m
  identical-looking existing transactions give min(k, m) candidates and the
  rest are new. Legitimate repeated payments survive whichever format came
  first. Identical rows inside one file are `repeated_in_file`, kept.
- Confirmation refuses any row that still needs a decision, both in the API
  and in the database function. Decisions are recorded as the owner's; a
  bulk action decides every candidate at once (link all, keep all, exclude
  all). A statement whose rows all match an overlapping period is reported
  as a likely duplicate statement; that report changes nothing by itself.
- CSV first, PDF second: PDF rows carry no references, so every row is a
  candidate; linking all adds the PDF as evidence and no transactions. PDF
  first, CSV second: the CSV rows are candidates by shape; linking lends
  each row's reference to the existing transaction, so a later replay of the
  referenced CSV matches by identity and needs no decision. Exact re-uploads
  of the same bytes are refused as before.

Lease-guarded mutations
- M6 bound only the lease release to the token. Now the writes of a
  processing step run inside database functions that take the job row lock
  and verify the job, token and expiry before writing: `stage_import`
  replaces the staged rows and marks the import staged in one transaction,
  `fail_import` records the failure. A worker whose lease was re-acquired
  gets `lease_lost` and its writes are refused; a cancelled import refuses
  staging with `invalid_state`. Object deletion follows only a successful
  guarded state change. Confirmation stays idempotent by revision.
- Deadline: each step carries a 100 s processing budget checked between
  pages and phases; leases last 180 s; the deployment's function limit is
  300 s; reads retry once with a 10 s client timeout, so a single read costs
  at most about 20.5 s. A step that runs out of budget fails retryably with
  a reference and leaves the upload in place.

Migrations
- 0009: `format` accepts `pdf`, object paths accept `.pdf`, the bucket
  allows `application/pdf`, `import_rows.page_number` and `decision_by`,
  `assert_lease`, `stage_import`, `fail_import`, and `confirm_import` with
  the undecided-row refusal and reference lending.
- 0010: `confirm_import` casts the format-derived source type to the enum;
  0009's CASE over string literals produced text, which PostgreSQL will not
  assign to an enum column, so confirmation failed at runtime on the
  development project although the function compiled. Found by the
  development-project checks before any preview existed.

## Verification

- Unit tests: extraction over every fixture (layouts, wrapped lines,
  repeated headers, identical payments, unreadable amount, missing line,
  wrong closing balance, injected text, refusal codes, deadline), matching
  (identity, conflicts, multiplicity, reverse order, assessment), route tests
  against the in-memory stand-in (PDF flow with page provenance, unsupported
  PDFs, CSV then PDF and PDF then CSV, repeated payments, stale-lease
  staging refusal, deadline).
- Development project through the running API with temporary resources:
  the import flow check (PDF isolation, guarded staging, lease tokens), the
  five pack PDFs sequentially, and the cross-format runs in both orders.
  Results are recorded in the checklist.

## Amendment 2026-09-13: findings from the pre-merge review

The review before merging M7 found one extraction defect and three
correctness gaps. All are fixed on the branch; migration 0012 carries the
database half.

Continuation lines. Merging a line into the description above it now requires
that the line sit on the same page, directly under the line it continues, and
within 1.5 times the line spacing measured in that document. The spacing is
the lower quartile of the gaps between adjacent table lines, so the large jump
from the last row to the page footer does not widen the allowance. Text that
appears with the same content at the same height on more than one page is
page furniture and is skipped; lines shaped like a posting are excluded from
that test, so two identical transactions can never be mistaken for a banner.
Positions are page-local, so a line on one page is never treated as
continuing a row on another.

Nothing transaction-shaped is dropped. A line whose date, description and
amount columns are all filled but whose date and amount cannot be read is
kept as a row and flagged, where the owner sees it, instead of being
discarded. A page that carries transaction-like lines but no column header is
refused with `pdf_layout_unsupported` naming the page, rather than skipped in
silence.

One reference, one transaction, per account. `confirm_import` checked
uniqueness across both import formats before inserting a transaction but only
within the target's own format before lending a reference to one, so a manual
link could leave a CSV and a PDF transaction sharing a reference. Nothing
enforced the rule either: two confirmations running at once could both pass
their checks. A partial unique index on `(account_id, external_id)` for the
import source types now makes it an invariant, the lending check uses the same
scope as the insert check, and confirmations into one account are serialized
by an advisory lock so the checks decide the outcome instead of racing into
the index. Existing data was inspected read-only before the index was created
and held no violation.

Keeping a row whose reference the account already holds is refused where the
owner can see it, per row and in bulk, instead of only at confirmation where
it refuses the whole file. The review page does not offer the option for such
a row. The database check stays: it is the invariant, and the route's refusal
is a courtesy.

Cancellation is atomic. `cancel_import` ends the import, invalidates any lease
still open and removes the staged rows in one transaction, taking the job rows
before the import row so it cannot deadlock with `stage_import`. A parse that
returns afterwards finds its token rejected and the import in a state staging
refuses. The uploaded object is removed after that transaction and recorded
separately, because Storage can fail on its own; a failed removal leaves
`object_deleted_at` null and is retried by cancelling again or by the sweep.

## Limitations

- Coverage is the fixture list. Real bank exports differ in ways these
  fixtures do not model; each new layout needs its own fixture before support
  is claimed.
- Column assignment relies on a header line with recognizable names; tables
  without a header, multi-column page layouts and statements that print
  amounts as words are refused rather than guessed.
- Statement metadata detection is keyword-based; a statement without such
  labels reconciles against its running balance column or not at all.
- No OCR and no model-assisted extraction; scans are refused.
- A page footer printed one line below the last transaction of a single-page
  statement, inside the description column and at the table's own line
  spacing, is indistinguishable from a wrapped description by position alone.
  The repeated-position rule below catches it on any statement of two pages
  or more, which is where footers normally live; on a one-page statement it
  would still be merged. No fixture or pack file prints one there.
- Parsing time on an adversarial file is bounded by the 10 MB file limit, the
  20 page limit, the 500 KB extracted-text limit and the platform's 300
  second function limit. The 100 second processing deadline is checked
  between pages and between phases, so it does not bound the time spent
  inside one page. No pathological file has been measured.
